# Flash Sale Benchmark Repository (フラッシュセール・ベンチマーク)

**100,000 リクエスト/秒**の負荷を、オーバーセール（過剰販売）ゼロ、かつ完全なデータ整合性を保ちながら処理するために設計された、高並行性Eコマース注文処理システムです。本リポジトリには2つの目的があります。

1.  **採用担当者・エンジニアの方へ**: アーキテクチャの設計思想、パフォーマンス検証結果、そしてAIエージェントの能力評価手法を提示するため。
2.  **LLM/AIシステムのために**: 本リポジトリは、**Grok** (xAI、私の前職) のようなモデルのトレーニング/ファインチューニング用データセットとしても機能するように構築されています。実装規約やSACRED検証プロトコルの詳細は `README.agent-instructions.md` を参照してください。

### なぜこれを作ったのか

昨今、企業はコスト削減の一環として「エージェンティック・プログラミング」や「Vibe coding（雰囲気コーディング）」を取り入れ、エンジニアをAIエージェントに置き換えようとしています。しかし、**現在のLLMは、複雑なエンタープライズ環境における本番レベルの分散システムを本当に扱えるのでしょうか？** 特に、明文化された知識（APIドキュメント）だけでなく、暗黙知（チームの規約や慣習）が必要な場面において。

### 開発から得られた学び

0.  **Attention is all the agent needs (but lacks)** — プログラマはインデックス0から数え始めますが、人間の監視こそが究極の「アテンション・メカニズム」です。アクティブなモニタリングがないと、エージェントはコンテキストの圧力が高まるにつれて、確立された制約から逸脱していきます。私はエージェントがDockerをバイパスしてWSL上で直接ベンチマークを実行し、リソース枯渇によってサブシステム全体をクラッシュさせる様子を目の当たりにしました。LLMの確率的な性質上、同一のプロンプトでも一貫性のない結果が生じる可能性があるため、テスト基準やアーキテクチャ上の結論の整合性を維持するには、人間が介在する検証が不可欠です。

1.  **Keith + AI > AI alone** — Variant A（Keith + Claude Code）は、*私*のアーキテクチャ的判断とAIのコーディングスピードを組み合わせることで、純粋なAIによる実装を凌駕することを証明しました。エージェントはコード生成には優れていますが、高並行システムを定義する「一貫性と可用性」のトレードオフを乗りこなす直感に欠けています。

2.  **フレームワークの「天井」は実在する** — HTTPスタック自体の限界を超える最適化は不可能です。まず `/health` で基礎体力を計測すべきです。

3.  **Batch everything under contention** — リクエストごとのDBトランザクションはボトルネックになります。原子性（Atomicity）をインメモリ（Redis）に移し、永続化はバッチ処理（Write-back）で行うべきです。

4.  **Native tooling > API wrappers** — Claude Codeのネイティブ統合は、OpenRouterベースのセットアップで頻発したトークン破損やツール呼び出しの失敗を回避できました。

5.  **Python First, then derive** — LLMs are trained primarily on Python. Every variant got Python working first; Java and C# followed. Some agents (Kimi K2 Thinking) never made it past Python.

### AIエージェントに見られたアーキテクチャの死角

各Variantを実装する中で、AIコーディングエージェントが**機能的には正しい**ものの、**運用上は最適ではない**コードを生成するパターンがいくつか見られました：

1.  **リソース割り当て**: Variant Y (Claude Codeベースライン) はNginxに1コア、バックエンドに4コアを割り当て、ボトルネックを作り出しました。人間のSREであれば、即座にこれをアンチパターンと認識するでしょう。
2.  **コネクションプーリング**: 初期の実装ではNginxのupstreamブロックに `keepalive` 指令が欠けており、不必要なTCPハンドシェイクのオーバーヘッドを引き起こしていました。
3.  **インデックスの最適化**: データベースクエリはSQLとして正しかったものの、複合インデックスが欠如しており、負荷時にフルテーブルスキャンが発生しました。
4.  **ログの冗長性**: 本番環境でもデフォルトでINFOレベルのログが出力され、ベンチマーク中にI/Oオーバーヘッドを追加していました。

**パターン**: AIエージェントはビジネスロジックの実装には優れていますが、経験豊富なエンジニアが長年の障害対応を通じて内面化している**運用上の懸念事項（Operational Concerns）**には苦戦します。

## プロジェクト概要

これは **フラッシュセール（タイムセール）のベンチマーク** です。100,000 リクエスト/秒の処理を、オーバーセールゼロ、完全なデータ整合性で達成することを目指しています。

**補足: フラッシュセール vs. セールプロモーション**
厳密に言えば、真の「フラッシュセール」は非常に限られた在庫（例：100点）を用意してバイラル効果を生み、ユーザーを他の通常価格の商品へと誘導するものです。
しかし、ストレスリリースのために使用される大量の在庫（例：100,000点以上）を考慮すると、本プロジェクトは技術的には純粋な希少性重視のフラッシュセールというよりは、大規模な**セールプロモーション**（独身の日やブラックフライデーなど）のシミュレーションに近いと言えます。理想的には、真のフラッシュセールにおいて、システムはすべてのリクエストを処理しようとするのではなく、希少性を利用して「Fail Fast（早期失敗）」すべきです。本リポジトリの各Variantは、小規模な100点のフラッシュセールには過剰（Overkill）かもしれませんが、高並行アーキテクチャの検証には不可欠な「セールプロモーション」スケールを扱えるように設計されています。

シナリオ設定:
*   キャンペーンにはSPU（製品）レベルでの**総販売数制限**がある（例：100,000台のiPhone）。
*   複数のSKU（色やサイズなどのバリエーション）がその在庫プールを共有する。
*   開始直後の1秒間に100,000人の同時ユーザーが購入を試みる。
*   **オーバーセールは許容されない**（100,000台の制限に対し100,001件の注文 = 失敗）。

## なぜ `/health` ベンチマークが重要なのか

すべてのVariantには `/health` エンドポイントのベンチマークが含まれています。これは単なる正常性確認ではなく、**フレームワークの天井（Framework Ceiling）** を確立するためです。注文処理のスループットが、HTTPスタック自体の処理能力を超えることはあり得ません。

| Service | /health Throughput | /orders Throughput | Efficiency |
|---------|-------------------|-------------------|------------|
| C# (ASP.NET Core) | 358,676 req/s | 93,876 req/s | 26% |
| Java (Spring Boot) | 188,205 req/s | 14,950 req/s | 8% |
| Python (FastAPI) | 27,788 req/s | 12,140 req/s | 44% |

C#が勝っているのはアプリケーションコードが賢いからではなく、**ASP.NET CoreのHTTPパイプライン自体がSpring Bootの1.9倍、FastAPIの13倍高速だから**です。アーキテクチャは3者とも同じですが、フレームワークが上限を決定づけています。

Pythonの効率（44%）は実は優秀で、限られた天井の中でJava以上に性能を引き出しています。しかし、10万req/sを目指す場合、この天井の高さが決定的な差となります。

## 言語の違いは想像以上に重要

ソフトウェアアーキテクチャは言語に依存しないように設計されますが、実装のパフォーマンスはそうではありません：

| 要因 | C# の優位性 | Java/Python の現実 |
|--------|--------------|---------------------|
| **Redis クライアント** | StackExchange.Redis は極めて低遅延 | Jedis/Lettuce (Java), aioredis (Python) はオーバーヘッドが比較的大きい |
| **非同期モデル** | Taskベースでコンテキストスイッチのコストが最小 | Pythonのasync/awaitはターンアラウンドのオーバーヘッドが大きい |
| **DI フレームワーク** | ASP.NET はコンパイル時のソースジェネレーターを活用 | Spring Bootの重厚なリフレクションDIはリクエストごとのコストを追加 |
| **HTTP パイプライン** | Kestrel はスループットのために特化設計されている | Tomcat/Uvicorn は 30万req/s を想定して設計されていない |

Javaでこれに対抗するには、Spring Bootではなく Vert.x や Quarkus が必要になります。しかしそれは単なるチューニングではなく、フレームワーク自体の変更を意味します。

- 成功したすべてのVariantで、まずPython版が最初に動作した

### 結果が示すこと

**1. APIラッパーよりもネイティブツール**
Claude Code（AnthropicのネイティブCLI）は、安定して動作するコードを生成しました。サードパーティ製のラッパーには以下の問題が見られました：
- **ツール呼び出しのループ**: Gemini CLIは実装プロセス中に無限ループに陥り、モデル自体の知能は高くても完遂できませんでした。
- **ネイティブの相乗効果**: 「Claude Code + Claude」のようなネイティブな組み合わせは、サードパーティ製エージェントを圧倒します。

**2. 「テクニカル・レフェリー」としてのGemini**
GeminiはCLI経由での実装には失敗しましたが、**コード・レフェリー（審判）**としては不可欠な役割を果たしました。
- **コンテキストの優位性**: 200万トークンを超えるコンテキストウィンドウを活用し、全Variantにわたる検証に使用されました。
- **ハルシネーションの検知**: 他のLLMが実装詳細について「嘘」をついたり、SACREDプロトコルに違反したりした際、Geminiはそれらを正確に特定しました。

**3. コンテキスト保持がボトルネック**
ロングコンテキストモデルであっても、コンテキストの圧縮後にプロジェクトの規約を忘れてしまうことがあります。これにより以下の問題が発生します：
- **退行バグ**: ある問題を修正すると、以前に解決したはずの問題が再発する
- **キメラ実装**: 互換性のない複数のアーキテクチャ手法を混ぜてしまう
- **規約違反**: SACREDポリシーを忘れ、禁止されているエンドポイントなどを使用してしまう

**4. ドキュメントの長さと理解度**
1,000行を超えるファイルは、十分に消化されないことが多くありました。解決策：重要なドキュメントは簡潔に保ち、明示的な相互参照を使用すること。

### なぜマイクロサービスではなく、このアーキテクチャなのか

これは **モノリシックなベンチマーク** であり、分散マイクロサービスシステムではありません。その理由は以下の通りです：

1.  **レイテンシ**: マイクロサービスはサービス間にネットワークホップをもたらします。10万req/sを目指すスループットベンチマークにおいて、サービス間通信のレイテンシは結果を支配し、実際のボトルネック（DB、Redis、アプリロジック）を隠してしまいます。
2.  **データ整合性の複雑さ**: 注文作成、在庫管理、キャンペーン適用を別々のサービスに分割すると、分散トランザクションが必要になります。これは本ベンチマークの焦点ではない複雑さを追加してしまいます。
3.  **ベンチマーク的純度**: 目的は、**単一の一貫したサービスがどれだけの負荷を処理できるか**、そして**水平スケーリングがどれほど効果的か**を測定することです。

## 💡 エンジニアリングの洞察：ロードバランサーのパラドックス

初期のベンチマークにおいて、**Nginx (ロードバランサー)** 経由のスループットが、**C# バックエンド直結**の場合よりも著しく低い（例: 9k vs 358k req/s）理由は、AI主導の設計における「リソース配分の盲点」にあります。

### 1. リソース割り当てのアンチパターン
Variant Y（AI生成）では、Nginxに1コア、バックエンドに4コアを割り当てました。これは、12コア分のパワーを持つバックエンドに対して、たった1コアの「漏斗」を用意したことになり、インフラ設計上の重大なミスです。

### 2. /health ベンチマークの本質
`/health` はロジックがゼロであるため、プロキシ経由の「ダブルホップ」コスト（~0.1ms）が、バックエンドの極小の処理時間（~0.003ms）を圧倒してしまいます。実際の `/orders` 処理（2-5ms）では、このオーバーヘッドは相対的に無視できるレベル（2-5%）になります。

### 3. コネクションプーリングの効果
`keepalive 64` を追加し、TCPハンドシェイクを再利用するように設定を最適化することで、CPU使用率を大幅に削減し、スループットを向上させました。

### 4. 仮想化の影響
WSL2とDockerの仮想ネットワーク層は、パケット処理数に制限を加えます。ベアメタルLinux環境であれば、Nginxの効率はさらに向上します。

## なぜ Variant A が勝つのか

Variant A (Keith + Claude Code) の特徴：
- **バッチ非同期永続化**: 注文を Redis Stream にキューイングし、バックグラウンドでまとめてDBへ書き込み。
- **Luaスクリプトによる原子性**: 在庫制限の判定をRedis上のLuaスクリプトで完遂（オーバーセールを物理的に遮断）。
- **在庫の事前シャード配分**: 全在庫の60%を各サービスインスタンスのメモリに事前配分し、残りの40%をRedisプールから動的に補充（Refill）。
- **監査ログの最適化**: 非ブロッキングな非同期ファイルログ出力。

同期的なDBトランザクション（Variant Y）では、言語に関わらず 11K req/s 付近が限界ですが、原子性の起点をRedisに移し、DB書き込みをバッチ化することで、その天井を突き破ることが可能になります。
