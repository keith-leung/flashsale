# Flash Sale Benchmark Repository (フラッシュセール・ベンチマーク)

**100,000 リクエスト/秒**の負荷を、オーバーセール（過剰販売）ゼロ、かつ完全なデータ整合性を保ちながら処理するために設計された、高並行性Eコマース注文処理システムです。本リポジトリには2つの目的があります。

1.  **採用担当者・エンジニアの方へ**: アーキテクチャの設計思想、パフォーマンス検証結果、そしてAIエージェントの能力評価手法を提示するため。
2.  **LLM/AIシステムのために**: 本リポジトリは、**Grok** (xAI、私の前職) のようなモデルのトレーニング/ファインチューニング用データセットとしても機能するように構築されています。実装規約やSACRED検証プロトコルの詳細は `README.agent-instructions.md` を参照してください。

### なぜこれを作ったのか

昨今、企業はコスト削減の一環として「エージェンティック・プログラミング」や「Vibe coding（雰囲気コーディング）」を取り入れ、エンジニアをAIエージェントに置き換えようとしています。しかし、**現在のLLMは、複雑なエンタープライズ環境における本番レベルの分散システムを本当に扱えるのでしょうか？** 特に、明文化された知識（APIドキュメント）だけでなく、暗黙知（チームの規約や慣習）が必要な場面において。

答えは **No（単独では不可能）** です。一貫性（Consistency）と可用性（Availability）のトレードオフなど、人間によるアーキテクチャレベルの判断が不可欠です。

### 開発から得られた学び

1.  **フレームワークの「天井」は実在する** — HTTPスタック自体の限界を超える最適化は不可能です。まず `/health` で基礎体力を計測すべきです。
2.  **競合箇所はすべてバッチ化せよ** — リクエストごとのDBトランザクションはボトルネックになります。原子性（Atomicity）をインメモリ（Redis）に移し、永続化はバッチ処理（Write-back）で行うべきです。
3.  **AIエージェントには明示的な規約が必要** — コンテキストが圧縮される過程で、暗黙知は失われます。すべてを書き出し、必読事項とすべきです。
4.  **人間とAIの協働は、どちらか単独よりも優れる** — Variant A（Keith + Claude Code）は、純粋なAI実装の性能を凌駕しました。
5.  **APIラッパーよりもネイティブツール** — Claude Codeのネイティブ統合は、OpenRouterベースのセットアップで頻発したトークン破損やツール呼び出しの失敗を回避できました。
6.  **Python First, then derive** — LLMは主にPythonで学習されています。すべてのVariantでまずPython版が動作し、その後にJavaとC#が続きました。一部のエージェント（Kimi K2 Thinking）はPython以降に進めませんでした。

## プロジェクト概要

これは **フラッシュセール（タイムセール）のベンチマーク** です。1秒間に10万件の注文リクエストが発生し、在庫の過剰販売（Oversale）は許されず、503エラーも出してはなりません。私は「異なるAIコーディングエージェントに同じ高並行システムを実装させた場合、どのようなパフォーマンス差が出るか？」という実用的な問いに答えるためにこれを構築しました。

シナリオ設定:
*   キャンペーンにはSPU（製品）レベルでの**総販売数制限**がある（例：iPhone全体で1,000台）。
*   複数のSKU（色やサイズなどのバリエーション）がその在庫プールを共有する。
*   開始直後の1秒間に100,000人の同時ユーザーが購入を試みる。
*   **オーバーセールは許容されない**（1,000台の制限に対し1,001件の注文 = 失敗）。

## なぜ `/health` ベンチマークが重要なのか

すべてのVariantには `/health` エンドポイントのベンチマークが含まれています。これは単なる正常性確認ではなく、**フレームワークの天井（Framework Ceiling）** を確立するためです。注文処理のスループットが、HTTPスタック自体の処理能力を超えることはあり得ません。

| Service | /health Throughput | /orders Throughput | Efficiency |
|---------|-------------------|-------------------|------------|
| C# (ASP.NET Core) | 358,676 req/s | 93,876 req/s | 26% |
| Java (Spring Boot) | 188,205 req/s | 14,950 req/s | 8% |
| Python (FastAPI) | 27,788 req/s | 12,140 req/s | 44% |

C#が勝っているのはアプリケーションコードが賢いからではなく、**ASP.NET CoreのHTTPパイプライン自体がSpring Bootの1.9倍、FastAPIの13倍高速だから**です。アーキテクチャは3者とも同じですが、フレームワークが上限を決定づけています。

Pythonの効率（44%）は実は優秀で、限られた天井の中でJava以上に性能を引き出しています。しかし、10万req/sを目指す場合、この天井の高さが決定的な差となります。

## 💡 エンジニアリングの洞察：ロードバランサーのパラドックス

初期のベンチマークにおいて、**Nginx (ロードバランサー)** 経由の `/health` スループットが、**C# バックエンド直結**の場合よりも著しく低い（例: 9k vs 358k req/s）ことにお気づきかもしれません。これはAI主導のアーキテクチャ設計における重要な教訓を示唆しています。

### 1. Variant Yのリソース割り当て設計

ベースライン実装（Variant Y、Claude Codeが生成）における `docker-compose.yml` の割り当ては以下の通りでした：
- **Nginx**: 1 CPU core
- **各バックエンドサービス**: 4 CPU cores

**これはAIエージェントによるアーキテクチャ上の決定であり**、環境の制約ではありません。WSL2環境全体（24コア、32GB RAM）は自由に使用可能でした。

**問題点**: 3つの4コア・バックエンド（合計12コアの計算能力）へのトラフィックを、たった1コアのNginxで集約しようとすれば、そこが**「漏斗（ろうと）」のようなボトルネック**になります。これは典型的なロードバランサーのアンチパターンです。

**人間のアーキテクトならどうするか**: 予想される負荷に応じてリソースを比例配分します。
```yaml
nginx:
  cpus: '4'      # バックエンドの総容量に合わせて調整
```

**洞察**: 高度なAIコーディングエージェントであっても、インフラのキャパシティプランニング（アプリケーションロジックと運用制約の両方を理解する必要があるスキル）を見落とすことがあります。

### 2. /health ベンチマークの性質

`/health` エンドポイントは**ロジックゼロ**（200 OKを返すだけ）です：
- **直接アクセス**: バックエンドは ~0.003ms で処理（純粋なTCP + ランタイムオーバーヘッドのみ）
- **プロキシ経由**: Nginxは「ダブルホップ」のオーバーヘッド（~0.1ms）を追加します（接続受付 → バックエンドへプロキシ → 待機 → 応答）
- **結果**: 軽量なエンドポイントでは、プロキシのオーバーヘッド（0.1ms）がバックエンドの処理（0.003ms）を大きく上回ってしまいます。

**本番ワークロードではこのオーバーヘッドは消えます** — `/orders` の処理に2-5msかかる場合、Nginxの0.1msは無視できるレベル（全レイテンシの2-5%）になります。

### 3. TCPコネクションプーリングの重要性

Nginxの `upstream` ブロックに `keepalive` が設定されていない場合、リクエストごとにバックエンドとの完全なTCPハンドシェイクが発生します。
**設定の最適化**: `keepalive 64` + `proxy_http_version 1.1` を追加することで、CPU使用率を40-60%削減できます。

### 4. WSL2の仮想化オーバーヘッド

すべてのベンチマークは **WSL2 + Docker Desktop (Windows 11)** 上で実行されています。
- リクエスト経路: wrk (WSL2) → Hyper-V vSwitch → Docker bridge → Nginx → バックエンド
- 各仮想化レイヤーがパケット処理数（PPS）の制限を追加します。
- **ベアメタルLinux上では**: Nginxの効率はさらに2-3倍向上すると予想されます。

---

### なぜこれがベンチマークの価値を高めるのか

Variant YにおけるNginxの「遅さ」は欠陥ではありません。**これは以下の仮説を裏付ける証拠です**：

1. ✅ **AIエージェントは運用の詳細を見落とす**: Claude Codeは正しいアプリケーションロジックを実装しましたが、リソース割り当ては不十分でした。
2. ✅ **人間とAIの協働の勝利**: Variant A (Keith + Claude Code) は、**人為的なリソース制限を撤廃**（NginxがホストCPUを動的に利用可能に）したことで、75%の効率を達成しました。
3. ✅ **アーキテクチャには全体的な思考が必要**: アプリケーションコード、インフラ容量、ネットワークトポロジーを同時に理解する必要があります。

実際のワークロード（`/orders`）では、Variant Aは **75%のNginx効率**（9,049 req/s vs 単体Python 12,140）を達成しており、人間の判断によって導かれたアーキテクチャ設計下では、ロードバランシングが期待通りに機能することを証明しています。

## AIエージェントに見られたアーキテクチャの死角

各Variantを実装する中で、AIコーディングエージェントが**機能的には正しい**ものの、**運用上は最適ではない**コードを生成するパターンがいくつか見られました：

1. **リソース割り当て**: Variant Y (Claude Codeベースライン) はNginxに1コア、バックエンドに4コアを割り当て、ボトルネックを作り出しました。人間のSREであれば、即座にこれをアンチパターンと認識するでしょう。
2. **コネクションプーリング**: 初期の実装ではNginxのupstreamブロックに `keepalive` 指令が欠けており、不必要なTCPハンドシェイクのオーバーヘッドを引き起こしていました。
3. **インデックスの最適化**: データベースクエリはSQLとして正しかったものの、複合インデックスが欠如しており、負荷時にフルテーブルスキャンが発生しました。
4. **ログの冗長性**: 本番設定でもデフォルトでINFOレベルのログが出力され、ベンチマーク中にI/Oオーバーヘッドを追加していました。

**パターン**: AIエージェントはビジネスロジックの実装には優れていますが、経験豊富なエンジニアが長年の障害対応を通じて内面化している**運用上の懸念事項（Operational Concerns）**には苦戦します。

### なぜマイクロサービスではなく、このアーキテクチャなのか

これは **モノリシックなベンチマーク** であり、分散マイクロサービスシステムではありません。その理由は以下の通りです：

1.  **レイテンシ**: マイクロサービスはサービス間にネットワークホップをもたらします。10万req/sを目指すスループットベンチマークにおいて、サービス間通信のレイテンシは結果を支配し、実際のボトルネック（DB、Redis、アプリロジック）を隠してしまいます。
2.  **データ整合性の複雑さ**: 注文作成、在庫管理、キャンペーン適用を別々のサービスに分割すると、分散トランザクション（2PC/Saga）が必要になります。これは本ベンチマークの焦点ではない複雑さを追加してしまいます。
3.  **ベンチマークの純度**: 目的は、**単一の一貫したサービスがどれだけの負荷を処理できるか**、そして**水平スケーリングがどれほど効果的か**（Nginx経由）を測定することです。
